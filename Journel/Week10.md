### [DECISION] GPU clock ceiling is 1237 MHz, not 1377 (Nov 6)
- The board powered off repeatedly in MAXN: twice at the start of `01_calibrate.py`, and in the CPU+GPU stress test (`sched-harness/probe_stress.py`). GPU-only load at 1377 MHz for 90 s passed, so the supply is the limit once the CPU is busy too. Prof confirmed it is the original PSU.
- 1339 was tried first and dropped (only about 1 W under 1377). The study tops out at 1237 MHz (22.6 W vs 26.9 W at 1377, ResNet152 b=16). `config.DVFS_MAX_MHZ = 1237` cuts the policy's table, caps `Clock` (it refuses anything higher), is the calibration/first-batch clock, and is the fixed-clock baseline (829 and 1237). 9 clocks: 421 .. 1237. Lambda_cap at 1237 is about 200 req/s (215 at 1377); loads 40..180 req/s.
- The ResNet table itself still has 1377 rows (measured earlier, board survived); they are just never used.
- Harness is now ResNet-only (YOLO version archived in `archive/sched-harness-yolo/`).
- Nov 6 evening: with the 1237 cap, `01_calibrate.py` ran all model tables and the switch-cost test, then the board powered off in the 20 s idle-power step. Switch cost between models was +0.23 ms (alternating 17.53 vs 17.30 ms). The long calibration is the longest continuous GPU run in the setup, so it is replaced by `01b_profile_from_table.py` (service times from the dvfs_runtime table at the ceiling clock, idle power measured alone). `run_resnet.sh` also caps the CPU at 1.19 GHz (restored at exit) and logs `tegrastats` once a second to `tegrastats_session.log` (synced every 2 s), so a crash leaves the board's last power/temperature state on disk. `CALIB=full` brings back the long calibration.

### [CHANGE OF PLAN] Main run: CIFAR-10 inputs, 30-minute runs (Nov 7)
- Inputs are now 128 random CIFAR-10 test images (seed 0, `sched-harness/data/cifar10_128.npz`, built once by `make_cifar128.py`, 32x32 upscaled to 224 at start-up; stored BGR like the old pool). Random-init ResNets and a fixed-cost forward pass mean the pixels should not change latency; any effect would be on power (data-dependent switching), which is a reason to use real images anyway. The container and the PC could not reach the CIFAR mirrors, so the npz has to be built on a machine with network and copied to the board. `build_pool()` fails loudly if it is missing (no silent noise fallback).
- `config.DURATION_S` is 1800 s (env `DURATION_S` overrides for quick tests): 1888 s per run, 31.5 min. 65 runs = 34 h, 21 runs (5 alphas + 2 baselines, 3 loads, 1 seed, SLO 300) = 11 h, the old 585-run grid = 307 h. The pilot (60 s runs) is not comparable to the main run. Per-run job counts: 72k at 40 req/s up to 326k at 180 req/s. QUEUE_CAP stays 512.
- `LOCK_CLOCKS = False` means the `jetson_clocks` script is not used (it pins CPU, GPU and EMC at max). It is not the policy: the policy sets the GPU clock per batch through `Clock.set` (devfreq min=max pin), and the harness pins the top clock before warm-up.

The old top load 180 (90% of capacity) is no longer in the grid.
- Nov 7 main-run changes: (1) the fixed-clock baselines (`dvfs_fixed` 829 and 1237) are out of the plan (the class stays in `policies.py`); alpha = 0 is the closest thing to a baseline, it picks the fastest feasible clock. (2) The mix is `light3` (60/30/10 over r18/r50/r152). Lambda_cap for it is 327 req/s from the table at 1237 MHz (balanced3: 200), so loads 30/90/150 are 9%, 28%, 46% of capacity. (3) `dvfs_alpha` drops jobs whose deadline has already passed (arrival + D <= now), in every queue, at every decision, before it decides; the runtime logs them as dropped = 2 and the metrics count them as misses at every deadline. `config.DVFS_DROP_EXPIRED` (env `DVFS_DROP_EXPIRED=0` to switch off), `policy_counters` gets a `dropped` count. A job that is still alive but cannot finish in time is not dropped; it is served as a `miss` (least-slack queue at the top clock) and counts as a violation when it finishes late.

### [RESULT] Main run, first pass: light3, SLO 900, 5 alphas x loads 100/200/300, seed 0 (Nov 8)
- All 15 runs finished (1800 s window each, no drain timeouts, no overflow, no crashes, board under 48 C). Checks 1-6, 8, 9 pass in all runs; check 7 (tegrastats cadence) fails in 10 of 15: 8.1-8.3 Hz instead of 10, longest gap up to 415 ms. The energy-books check still passes. Summary script: `sched-harness/05_dvfs_summary.py` (cached per run, output `analysis/dvfs_summary.csv`, `clock_shares.json`).
- Energy per good request (mJ), alpha 0 / 0.25 / 0.5 / 0.75 / 1: load 100: 150.5 / 143.7 / 131.5 / 119.1 / 117.0. Load 200: 104.6 / 101.7 / 97.6 / 76.1 / 71.7. Load 300: 79.6 / 79.8 / 76.9 / 84.0 / 86.8 (the last two drop 17.9% and 24.8% of jobs).
- At 100 and 200 req/s, alpha 0 is a constant 1237 MHz (1 switch) and alpha 1 is a constant 829 MHz (2 switches), so the saving there (22% at 100, 31% at 200, mean board power 15.05 -> 11.70 W and 20.93 -> 14.36 W) is just 829 MHz vs 1237 MHz. 829 is the energy-optimal clock for every model and batch size. Zero violations at SLO 900 in all of those runs; p99 latency 94 -> 116 ms (load 100) and 146 -> 422 ms (load 200). A slower clock lets queues build, so batches grow (4.3 -> 10.1 mean at load 200), which adds to the saving. At SLO 300, alpha 1 at load 200 would violate 8.5%.
- At 300 req/s (92% of Lambda_cap) 829-905 MHz cannot keep up (alpha 1 serves 226 req/s, alpha 0.75 serves 246). The policy is deadline-feasible per batch but not rate-aware: it lets the queue age to the deadline (p50 latency 750-760 ms vs D = 900), then drops expired jobs. alpha 0 and 0.25 serve 300 req/s with zero drops; alpha 0.5 gets 76.9 mJ with 0.24% drops (about 3% better than alpha 0, one seed, not distinguishable from noise). Energy per offered request flatters the dropping policies (64 mJ for alpha 1); use energy per good request.
- Clock switch cost in MAXN is not 88 ms. In-run switches: median 1.6 ms, p95 2.2 ms, p99 7 ms (alpha 0.5, load 100: 40,759 switches, 72 s blocked in total, 4% of the run). The 88-94 ms figure is the one-off initial pin before warm-up (alpha 0 shows exactly one switch with mean 94 ms). The sampled gr3d_mhz matches the commanded clocks (830/1030/1200/1240), so the pin works. DVFS_SWITCH_MS = 88 makes check 1 and the hysteresis about 40x too pessimistic; this needs fixing before any rerun.
- Caveats: one seed per cell (no error bars; the 300 req/s differences of a few percent are not established), and with the fixed-clock baselines dropped nothing here shows that clock switching beats the best fixed clock; at 100 and 200 the best policy is a fixed clock. Only at 300 is the adaptive part doing anything.
- Nov 8, second pass (same policy, more data): `config` now plans seeds 0, 1, 2; SLO 900 and 300; 5 alphas plus fixed-clock baselines 829, 1033 and 1198 MHz (`dvfs_fixed`, which now also drops expired jobs, so baselines and policy are compared the same way); loads 100, 200, 300 req/s on light3. 16 policies per load and seed, 48 runs per seed, 144 in total; the 15 finished runs (seed 0, SLO 900, alphas) are recognised by name and skipped, so 129 to go, about 68 h (25 h per seed, seed 0 needs 33 runs, about 17 h). DVFS_SWITCH_MS is still 88 (policy unchanged on purpose, see the switch-cost result above). Resume with the same DEVICE_TAG (agx_xavier_jp511_main).
